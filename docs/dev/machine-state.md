# Machine state (`state.toml`)

> Part of the edamame contributor deep-dives. Index and project-wide conventions: [`AGENTS.md`](../../AGENTS.md). Sibling docs live in [`docs/dev/`](.).


[`crate::config::State`] holds the values edamame writes on its own — `seen_terminal_fingerprints`, `last_update_check`, `update_notified_for`, `last_version_seen`, and the daily-tip stamps `seen_daily_tips` and `last_tip_shown` — persisted to `state.toml` in the platform *data* directory, separate from the user-facing `config.toml`. The user-facing view is in [`configuration.md`](../configuration.md#machine-state-statetoml); the mechanics live here.

- **Why a separate file, not `[editor]` keys.** These are all bookkeeping, never settings, and one of them (`seen_terminal_fingerprints`) is inherently per-machine — so they had no business in a `config.toml` that users hand-edit and symlink across machines from a dotfiles repo. Moving them out keeps `config.toml` entirely human-owned. The user-facing on/off flags stay on `Config`: `check_for_updates` and `daily_tips` are real settings that happen to sit beside the stamps.
- **The daily-tip fields (`seen_daily_tips: Vec<u32>`, `last_tip_shown: u64`).** `seen_daily_tips` is the ids ([`crate::app::tips::Tip::id`]) already shown, so a tip never repeats; `last_tip_shown` is the once-a-day gate stamp, read exactly as `last_update_check` is (via [`crate::app::update_check::interval_elapsed`], the gate both share). Both were *born* in `State` — they were never `config.toml` keys — so unlike the four above they need no migration and are absent from `BOOKKEEPING_KEYS_BARE`. A `Vec`, not a set: TOML has no set type, the list stays small, and a stable order keeps the machine file's diffs quiet. The rotation and the update-vs-tip precedence live in [`crate::app::tip_notice`].
- **`State` is a plain serialize, unlike `Config::save`.** The file is machine-only, so there are no comments to preserve and no `toml_edit` merge — `State::save` writes `toml::to_string_pretty` outright. A missing or partial file loads as defaults (`#[serde(default)]`), and a parse error is edamame's own bug: logged, then treated as "no state recorded", with no warning modal (a machine file the user never touched can't have a user-facing error).
- **The data dir is [`Config::data_dir`], shared with the tracing log.** `state.toml` and the log both sit under `$XDG_DATA_HOME/edamame` (or the platform equivalent), distinct from the config dir. A future move to a non-roaming location would happen in that one function.
- **`--no-config` and test isolation suppress it too.** `State::load`/`State::save` gate on `config_reads_allowed()` / `config_writes_allowed()` — the same [`persistence`](../../src/config/persistence.rs) switch that guards the config dir, whose scope is deliberately broader than its name (it governs every file edamame persists, config dir *and* data dir). A suppressed session reads defaults and writes nothing.
- **One-time migration: seed before strip.** `Config::load` seeds `state.toml` from a legacy `config.toml`'s `[editor]` bookkeeping (`seed_state_from_legacy_config`) *before* `migrate_config_file_in_place` strips those keys — order matters, since the strip destroys the source. Seeding is a no-op once `state.toml` exists (an existing state file is authoritative and must never be clobbered by a stale `config.toml`), when the config file is absent/unparseable, or when it carries none of the keys (a fresh install stays fileless until edamame writes bookkeeping of its own).
- **The migration is fail-soft, and that is safe.** The strip runs regardless of whether the seed write succeeded, so a failed seed does drop the values from disk — but they are re-derivable bookkeeping, never user settings, so the worst cost is a repeated capabilities notice or a re-run update check on the next launch, not lost configuration.
- **Stripped keys must not warn.** [`BOOKKEEPING_KEYS_BARE`] is the single source of truth for the four *migrated* names (the daily-tip stamps are not among them — they never lived in `config.toml`). It drives both the strip (in `config::config`) and the unknown-key filter in `read_main_config` (which prefixes each with `editor.`), so an un-migrated file — including one a `--no-config` run can't rewrite — never greets the user with a modal about keys edamame itself moved. The filter stays narrow: a genuinely unknown key beside them still warns.
- **`App` owns a `State` beside its `Config`.** Writes go through `save_state_bookkeeping` → `State::save` (a bare save, no "Configuration updated" flash — the user changed no setting; shared by the update check, the post-upgrade stamp, and the daily tip), or `save_state_with_flash` when a state-only outcome does want the flash. The external-editor reload ignores the reloaded `LoadedConfig::state`: the user edited `config.toml`, not `state.toml`.

See also [`update-check.md`](update-check.md) and [`post-upgrade.md`](post-upgrade.md), whose stamps are the writers of these fields.
